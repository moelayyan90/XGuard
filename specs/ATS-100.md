# XGuard ATS-100 — Agent Transaction Safety Score

Version: 2026-08-25

ATS-100 is an open 0–100 structural runtime-readiness score for agent-initiated payments, commerce actions and tool transactions.

It exists because autonomous agents retry, overlap and execute asynchronously. A transaction that is safe when a human clicks once can become unsafe under orchestration, timeout recovery and concurrency.

ATS-100 is intentionally protocol-neutral. It can evaluate structural safety signals in x402, MPP, AP2, UCP, ACP, MCP, signed HTTP and generic HTTPS machine transactions.

## Scoring rubric

| Control | Weight | What earns full credit |
| --- | ---: | --- |
| Protocol identification | 15 | The transaction wire is structurally identifiable rather than ambiguous generic HTTP. |
| Idempotency | 20 | A state-changing request carries an explicit idempotency key; read-only requests receive full credit automatically. |
| Context binding | 25 | Authorization is visibly bound to the exact resource, recipient, amount, mandate or equivalent execution context. |
| Replay uniqueness | 15 | A nonce, mandate/payment/transaction ID, receipt or durable idempotency signal provides consume-once semantics. |
| Freshness window | 10 | A bounded validity period, expiry or signed timestamp is visible. |
| Traceability / authorization | 15 | A signature, authorization signal or stable request correlation identifier is present. |

Total: 100 points.

## Grades

- A: 90–100
- B: 80–89
- C: 70–79
- D: 60–69
- F: 0–59

## Important limits

ATS-100 is **not a certification** and does not claim that the remote merchant implementation behaves correctly. The public XGuard test evaluates the supplied sample structure and does not contact the target merchant endpoint.

A strong score means the sample exposes the major runtime controls needed for safe automated retries. It does not replace protocol-specific validation, payment-provider controls, fraud systems, legal compliance or production testing.

## Why these controls

The weighting prioritizes context binding and idempotency because agent systems amplify retry and replay failure modes. Current agent-commerce specifications and research explicitly call out idempotency, replay protection, context binding and mandate lifecycle enforcement as runtime concerns.

Reference material:

- Agentic Commerce Protocol idempotency proposal: https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/issues/120
- Zero-Trust Runtime Verification for Agentic Payment Protocols: https://arxiv.org/abs/2602.06345
- IMF note on agentic payments, authorization and programmable controls: https://www.imf.org/-/media/files/publications/imf-notes/2026/english/insea2026004.pdf

## Design principle

The protocol should be allowed to change. The transaction safety controls should not have to be reinvented every time it does.
